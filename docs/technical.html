Coding Standards & Rules

1. Python Style

RuleDetail
Type hintsAll public functions must have type hints. Use typing module (List, Dict, Optional, Any, Annotated).
DocstringsEvery public function/class needs a docstring. Follow the pattern in kb_manager/pipeline/orchestrator.py (Args/Returns sections).
AsyncUse async def for I/O-bound operations (DB, HTTP). Do NOT mix asyncio.to_thread() with asyncpg — thread-hop breaks the pool ("attached to a different loop").
Error handlingWrap external calls (HTTP, DB, model) in try/except. Log with log.warning()/log.error(). Fail closed on guardrails.
LoggingUse module-level logger = logging.getLogger(__name__). Do not print().
No comments on obvious codeComments only for why, not what.
ImportsStandard library → third-party → local. No wildcard imports.

2. FastAPI Patterns

RuleDetail
Pydantic modelsUse BaseModel for request/response bodies. Validate all inputs.
Factory patternUse create_app --factory (see work_rag_guardrails.api, work_rag_orchestrator.api).
EndpointsRESTful nouns. /v1/chat/completions, /v1/models, /health, /ready.
Timeoutshttpx.AsyncClient(timeout=120, trust_env=False) — bypass corporate proxy for localhost.
Status codesReturn proper HTTP status. Guardrails catches upstream errors and returns finish_reason="length" (valid Literal) instead of crashing with "error".

3. Database Patterns

RuleDetail
Async SQLAlchemyUse async_sessionmaker, AsyncSession. Always async with db.session() as session:.
pgvectorHNSW index for chunk embeddings. 1 - (embedding <=> CAST(:q AS vector)) for cosine.
Entity listsEntityList table: list_name, description, description_embedding (JSON), content_json. Always populate description_embedding via SentenceTransformerEmbedder.embed_texts().
MigrationsNone automated — schema changes via manual SQL + code updates.

Key Insights & Decisions

#DecisionRationaleDate
1 dense._ensure_model() instead of dense.model DenseSemanticIndex has no public .model attribute. All hasattr(dense, "model") guards were always False, silently disabling embedding in step-8 entity injection and /search/supplement. 2026-10-27
2 Entity lists embedded via embed_texts(title + desc) All 10 reason-code variants share identical generic descriptions. The list_name (title) is what distinguishes them. 2026-10-27
3 trim_supplemental() + 4KB total budget in build_context Triton Gemma has 8192-token context. 11 full entity lists = 663KB caused HTTP 500 context overflow (Triton 400: default_max_tokens negative). 2026-10-27
4 Guardrails finish_reason="length" not "error" Pydantic ChatCompletionChoice.finish_reason is a Literal of stop/length/content_filter. "error" crashed validation and masked the real upstream 400 context-overflow. 2026-10-27
5 should_clarify short-circuits on entity evidence When the supplement tool matches a dictionary (reason code, shareholder, etc.), clarify is counterproductive — the model can answer from entity rows directly. 2026-10-27
6 Code-token fallback in supplement search Cosine for queries like "MTX1" or "SBD1" is diluted by stopwords (~0.35 < 0.4 threshold). Mixed alphanumeric tokens appearing in list content guarantee a match regardless of cosine. 2026-10-27

Lessons Learned

  • Never assume hasattr(dense, "model") works. Always use dense._ensure_model() or dense._encode() on DenseSemanticIndex. Checked in kb_manager/web/routes/search.py at 5 sites.
  • Entity lists need explicit embeddings. The pipeline route constructed PipelineOrchestrator(database=db, chunker=chunker) without an embedder, so all 22 entity lists had description_embedding=None. Fixed by passing SentenceTransformerEmbedder().
  • Context window is the bottleneck. The 8192-token Triton limit caused silent 500s. Fixed by trimming entity payloads and capping build_context budget at 4000 chars.
  • Guardrails swallows upstream errors. A bare HTTP 500 hid the real Triton 400 until we reproduced in-process with the exact prompt_messages.
  • Persian query path matters. The KB uses preprocessor/persian.py + regex_persian.py for normalization, plus a 93-entry synonym map in query_expansion.py. Ignoring this breaks retrieval for Persian queries.

Git Workflow & Branch Protection

BranchPurposeWho can pushProtection

feature/*Individual dev workAuthorPR from feature → develop

PR Workflow

  1. Start from develop: git checkout develop && git pull origin develop && git checkout -b feature/your-change-name
  2. Make changes, run tests, verify.
  3. Commit with conventional prefix: git commit -m "feat(kb): add supplement entity-list tool path" (prefixes: feat, fix, docs, chore, refactor).
  4. Push feature branch: git push origin feature/your-change-name.
  5. Open PR from feature/your-change-name → develop; request at least one code review.
  6. Merge to develop after approval.
  7. Release to production: merge develop → main, then bash deploy/vast/stop.sh && bash deploy/vast/start.sh && bash deploy/vast/health.sh.

Branch Protection Rules (configure on GitHub)

For main / master: require PR before merging, 1 approving review, dismiss stale approvals, require status checks (CI: tests, lint, docs-toc), require branches up to date, require conversation resolution, restrict pushes to matching branches, no force pushes, no deletions, include administrators.

For develop: same as main, but can allow more flexibility if desired.

Submodule Workflow

# 1. Work in the component repo
cd components/knowledgebase   # or the component repo directly
git checkout -b fix/issue-name
# ... make changes ...
git commit -m "fix(kb): resolve asyncpg loop bug"
git push origin fix/issue-name
# Open PR on that component repo → main/master
# 2. After merge, advance the gitlink in the parent:
cd ..
git add components/knowledgebase
git commit -m "chore: advance knowledgebase submodule"
git push origin develop

Never commit component source changes directly in the parent repo — always go through the submodule.

Agent Onboarding — New Machine Setup

Prerequisites

  • Git installed
  • Python 3.11+ (KB) or 3.12+ (orchestrator/guardrails)
  • uvicorn, fastapi, httpx, sqlalchemy[asyncio], asyncpg
  • Access to the GitHub repos (credentials configured)

Step 1: Clone the umbrella repo with all submodules

git clone --recursive https://github.com/AliNikkhah2001/Work_Credit-RAG_Phase1.git
cd Work_Credit-RAG_Phase1

If already cloned without --recursive: git submodule update --init --recursive

Step 2: Verify submodule status

git submodule status --recursive

Expected output shows all submodules pinned to commits with - (not +). A + prefix means the submodule is out of sync — run git submodule update --recursive.

Step 3: Read agent context

cat agent-state/context/context.md
cat agent-state/context/todo.md
cat agent-state/architecture.md
cat agent-state/coding-standards.md

Step 4: Check current branch

git branch --show-current

Should be develop for integration work. Create feature branches from here: git checkout -b feature/your-change

Step 5: Verify services are running (if testing locally)

for p in 18000 8000 8200 8100; do printf "%s: " "$p"; curl -s --max-time 8 http://127.0.0.1:$p/health | head -c 120; echo; done

Step 6: Make changes

Follow the PR workflow in git-workflow.md: feature branch from develop, commit with conventional prefix, push feature branch, open PR → develop, code review → merge.

Step 7: Release (production)

git checkout main
git pull origin main
git merge --no-ff develop
git push origin main
bash deploy/vast/stop.sh
bash deploy/vast/start.sh
bash deploy/vast/health.sh
